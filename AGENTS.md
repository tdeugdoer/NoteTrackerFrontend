# NoteTrackerFrontend — учебный React-фронтенд для NoteTracker

Отдельный репозиторий с UI для проекта **NoteTracker**. Цель — не стать фронтенд-разработчиком, а
понять React на уровне, достаточном для интеграции с бэкендом и участия в обсуждении фронтенд-задач:
компоненты, props, state, события, списки, условный рендеринг, `useEffect`, маршрутизация и работа
с REST API.

Источник требований — файл **`plan`** в корне этого репозитория (не изменять). `AGENTS.md` переводит
план в правила. Если правило расходится с планом — приоритет у плана; если план молчит —
действуй по правилам ниже.

Бэкенд — отдельный репозиторий `D:\Study\Projects\NoteTracker` (контракты описаны в его `AGENTS.md`).

## Рамки: что изучаем и что нет

**Изучаем** (только по мере необходимости, на задачах NoteTracker):

- современный JavaScript: `fetch`, `async/await`, `Promise`, деструктуризация, модули;
- React: компоненты, props, `useState`, события, `map` + `key`, условный рендеринг, `useEffect`;
- TypeScript: типы DTO бэкенда, union-типы, `import type`, сужение `unknown`;
- React Router (базовый уровень), пользовательские хуки, `useSearchParams`;
- Axios — опционально, после рабочей версии на `fetch`.

**Не изучаем и не добавляем без явной просьбы** (это шум для цели обучения):

- менеджеры состояния: Redux, Zustand, MobX, Jotai, а также менеджеры серверного кеша
  (React Query/SWR);
- UI-библиотеки и киты: Ant Design, MUI, Chakra, Bootstrap, shadcn/ui, готовые модальные окна;
- метафреймворки: Next.js, Remix, SSR;
- тесты: Jest, Vitest, React Testing Library, Playwright;
- микрооптимизации: `useMemo`, `useCallback`, `React.memo`;
- вложенная маршрутизация, guard'ы маршрутов, авторизация, i18n;
- CSS-in-JS, препроцессоры (Sass/Less), если они не нужны конкретной задаче.

Правило: **каждая новая зависимость должна быть оправдана пунктом плана**. Если задача
решается штатными средствами React/JS — решать штатными.

## Интеграция с бэкендом

Сервисы запускаются из репозитория NoteTracker (`docker compose up -d`):

| Сервис          | Базовый URL              | Что даёт                        |
|:----------------|:-------------------------|:--------------------------------|
| note-service    | `http://localhost:8081`  | CRUD заметок                    |
| history-service | `http://localhost:8082`  | журнал событий (MongoDB)        |

Контракт (детали — в `NoteTracker/AGENTS.md`):

| Метод    | Путь                         | Тело запроса            | Ответ                        |
|:---------|:-----------------------------|:------------------------|:-----------------------------|
| `GET`    | `/api/notes`                 | —                       | `200` + `Note[]`             |
| `GET`    | `/api/notes/{id}`            | —                       | `200` + `Note`               |
| `POST`   | `/api/notes`                 | `{ title, content }`    | `201` + `Note`               |
| `PUT`    | `/api/notes/{id}`            | `{ title, content }`    | `200` + `Note`               |
| `DELETE` | `/api/notes/{id}`            | —                       | `204`                        |
| `GET`    | `/api/history`               | —                       | `200` + `ActivityLog[]`      |
| `GET`    | `/api/history?noteId={uuid}` | —                       | `200` + `ActivityLog[]`      |

Типы в `src/types/api.ts` повторяют DTO бэкенда **один в один** (не переименовывать поля):

```ts
type Note = {
  id: string          // UUID
  title: string
  content: string
  createdAt: string   // ISO-8601 Instant, не Date
}

type NoteRequest = {
  title: string
  content: string
}

type EventType = 'CREATED' | 'UPDATED' | 'DELETED'

type ActivityLog = {
  id: string                       // ObjectId (24 hex)
  eventType: EventType
  noteId: string                   // UUID
  noteTitle: string | null         // null, если заметка уже удалена
  eventTimestamp: string           // ISO-8601 Instant
  serviceName: string              // всегда "history-service"
}

type ProblemDetail = {
  type?: string
  title?: string
  status?: number
  detail?: string
  instance?: string
}
```

Правила контракта:

- **Не выдумывать поля и эндпоинты.** Если данных не хватает — менять бэкенд (сначала обсудив),
  а не изобретать поля на фронте.
- Валидация на бэкенде: `title` — обязателен, до 255 символов; `content` — до 10 000.
  Клиентская проверка повторяет эти лимиты только для удобства, сервер — источник истины.
- История приходит **уже отсортированной** по `eventTimestamp` по убыванию — на фронте не
  пересортировывать.
- `noteTitle === null` — штатная ситуация (заметка удалена или note-service недоступен):
  показывать `[заметка удалена]` серым текстом, а не ошибку.
- `id`/`createdAt`/`eventTimestamp` — строки из JSON. Форматирование дат — только при рендере
  (`new Date(value).toLocaleString('ru-RU')`), не в слое API.
- `noteId` в фильтре — UUID. Невалидный UUID бэкенд отклонит (`400`), поэтому проверяй формат
  на клиенте и не отправляй заведомо неверный запрос.

### CORS

Origin фронтенда — `http://localhost:5173`. Сейчас в NoteTracker CORS **не настроен**, браузер
заблокирует запросы. По плану CORS настраивается на бэкенде (note-service и history-service —
фронтенд ходит в оба напрямую): разрешить origin `http://localhost:5173`, методы
`GET/POST/PUT/DELETE/OPTIONS`, заголовок `Content-Type`.

- Не обходить CORS расширениями браузера, запуском Chrome с `--disable-web-security` или
  Vite-прокси: цель этапа — пройти именно CORS.
- Изменения CORS — в репозитории NoteTracker, отдельной правкой; фронтовый репозиторий только
  потребляет API.

### Данные и моки

- Работаем с **живым бэкендом**: моков и захардкоженных массивов в итоговом коде нет.
- Бэкенд недоступен — это состояние ошибки в UI («Не удалось загрузить заметки. Проверьте, что
  note-service запущен»), а не повод подставить демо-данные.
- Kafka и MongoDB фронтенд напрямую не читает: только REST-эндпоинты.

## Сетевой слой

- Все HTTP-вызовы — в `src/api/`. Компоненты и хуки не вызывают `fetch`/`axios` напрямую, а
  импортируют функции (`fetchNotes`, `createNote`, `updateNote`, `deleteNote`, `fetchHistory`).
- Базовые URL — константы в `src/api/config.ts`, не разбросаны по файлам.
- Один HTTP-клиент на проект. Начинаем с `fetch`; Axios допустим на этапе 3 как замена
  **внутри `http.ts`** — сигнатуры функций API не меняются, компоненты не знают о библиотеке.
- Ответы типизированы; на границе API `any` запрещён. Неизвестный ответ парсится как `unknown`
  и сужается проверками.
- Ошибки: единая функция преобразования неуспешного ответа в `ProblemDetail`/`ApiError`.
  Показывать пользователю `title`/`detail` от бэкенда (`400` — что не так с данными, `404` —
  заметки нет, `500` — сбой бэкенда/Kafka), а не голый `Failed to fetch`.
- `204` (DELETE) — без разбора тела.
- Сетевой сбой (бэкенд не запущен) и HTTP-ошибка — разные сообщения.

## Компоненты и состояние

- **Один компонент — одна ответственность.** `NoteForm` — ввод и отправка; `NoteList` — список;
  `NoteCard` — одна заметка из props; `HistoryTable` — таблица. Страница (`NotesPage`) собирает
  их и владеет данными.
- Props — типизированы, только необходимые данные и колбэки; данные передаются вниз, события —
  вверх.
- State — **как можно ниже**: локальное состояние остаётся в компоненте, поднимается только когда
  нужно соседям. Общее для страницы — в странице.
- **Не дублировать производные данные в state** (например, отфильтрованный список): вычисляй при
  рендере из исходного массива и фильтра.
- Загрузка/ошибка/пусто/данные — четыре явных состояния: `loading ? … : error ? … : items.length
  === 0 ? … : …`. Пустой список — не ошибка.
- Списки: `items.map(item => <NoteCard key={note.id} … />)`; `key` — стабильный id, индекс
  массива допустим только для никогда не меняющегося списка.
- События: `onClick`, `onChange`, `onSubmit` с `preventDefault`; кнопки без отправки формы —
  `type="button"`; на время запроса кнопки/поля `disabled`.
- Формы — контролируемые (`value` + `onChange`); после успешного создания — очистить форму и
  обновить список.
- `confirm()` перед удалением допустим (по плану) — модальные библиотеки не добавляем.
- `<StrictMode>` включён: в dev эффекты вызываются дважды, это не баг. Запросы в `useEffect`
  должны быть прерываемыми (`AbortController`/`AbortSignal`, отмена в cleanup), чтобы не было
  гонок и обновления размонтированного компонента.
- `useEffect` — только для синхронизации с внешним миром (запрос данных, подписка). Для
  вычислений из props/state эффект не нужен.
- Пользовательский хук (`useNotes`, `useHistory`, `useFetch`) извлекается, когда логика
  повторяется или страница разрастается, — не заранее.
- Базовая доступность: `<label>` у полей ввода, `alt` у картинок, осмысленный текст кнопок.

## Маршрутизация и URL-состояние

- React Router подключается на этапе 4: `BrowserRouter`, маршруты `/notes` (список + форма) и
  `/history` (журнал), навигация — `Link`/`NavLink`. `/` перенаправляет на `/notes`.
- Никакой вложенной маршрутизации, guard'ов, lazy-загрузки — только два плоских маршрута.
- Фильтр истории (этап 5) живёт **в URL**, а не в локальном state: `useSearchParams`,
  `?noteId=<uuid>`. Страница читает параметр, отправляет его в `GET /api/history?noteId=…`,
  пустой результат показывает явным сообщением («По этой заметке событий нет»).
- Состояние фильтра должно переживать перезагрузку страницы и ссылку, отправленную другому
  человеку.

## TypeScript

- `strict: true` в `tsconfig.app.json` (если ещё не включён — включить в рамках этапа 1).
- `any` — только как временная заглушка при прототипировании, в завершённой задаче его быть не
  должно; для неизвестных данных — `unknown` + сужение.
- `@ts-ignore` запрещён; `@ts-expect-error` — только с комментарием, почему.
- `verbatimModuleSyntax` включён: импорт типов — `import type { Note } from './types/api'`.
- `erasableSyntaxOnly` включён: **`enum` и parameter properties в конструкторах запрещены**
  (они не стираются). Вместо `enum` — union-тип: `type EventType = 'CREATED' | 'UPDATED' |
  'DELETED'`.
- `noUnusedLocals`/`noUnusedParameters`: неиспользуемые переменные и параметры ломают сборку.
- Типы — PascalCase, функции/переменные — camelCase, компоненты — PascalCase.
- Явные типы для props и результатов API-функций; вывод типов — для локальных переменных.

## Стили
